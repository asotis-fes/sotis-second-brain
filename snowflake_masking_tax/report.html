Snowflake Masking Tax — Experiment Matrix

Run ID 20260610a · alex.sotis@betfanatics.com · 2026-06-10

What this experiment measures

Quantify the wall-clock and credit cost of adopting Snowflake column masking policies on FES Data workloads. Four phases, increasing realism: a smoke test, a per-row-cost microbenchmark, a production-realistic dbt model rebuild, and a real consumer query pattern (Growthloop).

Each phase tests a defined matrix of policy variants (no masking, SHA2 hash, constant-return, role-conditional) and role contexts (user has PII access vs. doesn't). The view-based PII handling alternative is out of scope.

Findings

  • Hash masking adds essentially zero cost on the prod 3XL warehouse — the per-row SHA2 work parallelizes across 32× the compute of Phase 2's SMALL warehouse.
  • Constant-return masking is faster than no policy at all by ~14.5% — the optimizer skips the column scan for constant projections.
  • Correctness caveat: the column_intersection_row_hash macro hashes masked values deterministically — upstream PII changes won't reflect in row-hash, so fangraph_last_updated_timestamp won't bump.
  • Verified controls: zero warehouse contention from other users; all runs on 3XL; result cache disabled; cold-start consistent.

Findings

  • For growthloop (has PII role): adopting hash masking adds +2.0%, const masking adds +0.7%. Both well within noise — essentially free for their real workload.
  • HASH plaintext ≈ CONST plaintext (111.2s ≈ 109.9s) — confirmed: both hit the THEN val branch; the unused ELSE doesn't matter.
  • Even masked-branch tax is small (+5%) on Large warehouse — vastly less than Phase 2's +113% microbenchmark prediction. Parallelism + workload dilution at scale.
  • Constant masking is >10% faster than baseline on the masked branch — optimizer elides constant projections.
